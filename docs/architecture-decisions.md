# RPG Architecture Decisions

Architecture decision record. Dates indicate when decisions or deferrals were recorded. Rows labeled provisional describe prototype choices rather than final gameplay policy. The maintained project copy is `docs/architecture-decisions.md` in the Juego repository.

| Decision | Reason | Date |
| --- | --- | --- |
| Build for a multiplayer RPG with modest scale; prioritize adaptation and content expansion. | The initial architecture should support new quests, spells, and character mechanics without optimizing prematurely for massive scale. | 2026-10-08 |
| Launch with text play and keep the world engine independent of presentation. | Text, browser plug-in, and video game interfaces should share the same world state and gameplay actions. | 2026-10-08 |
| Represent characters, items, rooms, and quests as entities with stable identities. | A common identity model supports references and relationships across different types of content. | 2026-10-08 |
| Compose entities from extensible, structured components. | New capabilities can be added without expanding a fixed character or item schema for every mechanic; defined component structures support validation. | 2026-10-08 |
| Separate reusable content definitions from individual world instances. | Many objects can share a definition while instances hold unique ownership, durability, inscriptions, or other state. | 2026-10-08 |
| Model effects as first-class definitions with identities. | Conditions, contributions, and lifetimes can be described and reused independently of the items or spells that supply them. | 2026-10-08 |
| Create effect instances that identify their definition, source, target, creation time, and instance state. | Individual applications need their own expiration, charges, and provenance even when they share behavior code. | 2026-10-08 |
| Separate an effect's attachment from its current activation. | A worn ring can remain attached while inactive, then become active when its intelligence requirement is met. | 2026-10-08 |
| Keep an item separate from the effect it creates. | Consuming a scroll can remove the item while its temporary effect continues to exist. | 2026-10-08 |
| Represent behavior code as addressable, versioned modules referenced by the model. | Unique mechanics can be introduced as new modules, and explicit versions identify the implementation used by a definition. | 2026-10-08 |
| Pass parameters to shared behavior modules rather than copying code into every instance. | Common mechanics such as attribute thresholds and multipliers can be reused with different values. | 2026-10-08 |
| Give behavior modules explicit roles: condition, contribution, action, and lifetime. | Defined interfaces distinguish applicability, proposed effective-state changes, intentional world transitions, and effect duration. | 2026-10-08 |
| Store mutable per-instance state outside shared behavior modules. | Multiple applications can share implementation code while retaining different targets, expiration times, and charges. | 2026-10-08 |
| Keep base facts separate from derived effective state. | Temporary modifiers should not overwrite original attributes; effective values can later be cached without becoming the authoritative base facts. | 2026-10-08 |
| Preserve effect provenance through source and target references. | The engine can explain attribute changes and identify effects associated with an item or action. | 2026-10-08 |
| Use the ring-and-scroll scenario as a reference example. | Base strength 10 and intelligence 12; an equipped ring grants 10% strength at intelligence >= 13; a temporary 10% intelligence effect yields intelligence 13.2 and strength 11 if fractional values are retained. | 2026-10-08 |
| Defer rounding, stacking, dependency evaluation, ordering, and cycle handling. | These are evaluation rules to design separately; rounding must be explicit because it can change threshold activation. | 2026-10-08 |
| Defer the development language and behavior execution runtime. | Go and TypeScript/Node remain candidates; the model should not assume a particular runtime yet. | 2026-10-08 |
| Defer persistence and physical storage of behavior implementations. | Logical structure can be established before choosing a database or whether modules are stored directly in the model or referenced from a code registry. | 2026-10-08 |
| Treat an entity as the world instance; do not introduce a separate entityInstance type. | Definitions hold reusable templates; entities hold identities and current base state, avoiding two overlapping instance concepts. | 2026-10-08 |
| Give behaviors a supplied read-only world view and explicit inputs, with structured results. | Modules stay independent of persistence and presentation; the engine can validate, explain, and apply outcomes. Prototype action methods still mutate validated in-memory state directly. | 2026-10-08 |
| Separate condition failure from behavior execution failure. | A legitimate inactive effect must be distinguishable from broken code or invalid content; prototype execution failures throw errors. | 2026-10-08 |
| Supply simulation time through the behavior context. | Effect lifetimes and progression timestamps do not depend on a module reading the wall clock; controlled randomness is deferred until needed. | 2026-10-08 |
| Use TypeScript interfaces and Node.js for the initial scaffold; keep core/game separate from prototyping. | The prototype tests the model without committing the final production language or promoting the limited evaluator into the core contract. | 2026-10-08 |
| Represent classes and spells as reusable definitions with typed components. | New class and spell content fits the existing definition system without introducing separate identity mechanisms. | 2026-10-08 |
| Store class membership and progression on the character, independently of its entity definition. | Alice can be an adventurer entity and a Sword Wizard; class progression does not require replacing her entity template. | 2026-10-08 |
| Keep class spell offerings and character spell selections separate. | Eligibility belongs to reusable class rules, while individual choices belong to character state. | 2026-10-08 |
| Describe class spell offerings with minimum class levels and prerequisite spell references. | Classes can vary spell availability through content data; sample names and level gates are illustrative rather than settled balance decisions. | 2026-10-08 |
| Derive current spell-learning eligibility rather than storing a duplicate eligibility list. | Eligibility responds to levels and selections without maintaining a second mutable representation. | 2026-10-08 |
| Record current class level and achieved-level history using simulation timestamps. | The model captures both current progression and which levels were achieved; sample historical timestamps are placeholders. | 2026-10-08 |
| Record each spell selection with its learning time, class level at learning, and separate mastery rank. | Knowing a spell, class advancement, and spell mastery represent different dimensions of progression. | 2026-10-08 |
| Reference versioned behavior modules for class equipment restrictions; store armor categories on item definitions. | A reusable category condition permits robes and rejects plate without hard-coding Sword Wizard identity into equipment handling. | 2026-10-08 |
| Keep equipment slots separate and retain equipped items in owned inventory. | Finger and body equipment can coexist, and wearing an item does not change its ownership. | 2026-10-08 |
| Validate equipment and learning actions before changing world state. | Rejected plate armor, unavailable spells, and duplicate learning must leave existing state intact. | 2026-10-08 |
| Allow multiple class progression tracks in the data shape; defer full multiclass rules. | The model leaves room for expansion without claiming that advancement, shared spells, or conflicting permissions are already resolved. | 2026-10-08 |
| Provisional: combine class equipment rules with all-of semantics and evaluate them when equipping. | This is sufficient for the single-class prototype. Conflict policies and revalidation after class or rule changes remain open. | 2026-10-08 |
| Provisional: retain fractional attributes, compound multipliers, resolve dependencies on demand, and reject cycles. | These choices make the reference scenario runnable without establishing final rounding, stacking, or general cyclic-evaluation rules. | 2026-10-08 |
| Defer progression economy and spell execution mechanics. | Experience points, level costs, selection budgets, mastery advancement, spell casting, and respecialization need separate design; prototype level advancement is an admin operation. | 2026-10-08 |
| Defer a generic action executor, full schema validation, behavior registry, and module sandboxing. | Core interfaces describe the intended boundary, while the prototype uses trusted fixtures, parameter checks, and a limited dispatcher. | 2026-10-08 |
| Call applicability-check modules predicates; call entity conditions status effects. | The two meanings of condition need distinct names. PredicateBehavior, PredicateResult, and effect predicates replace the original condition-interface names. | 2026-10-08 |
| Represent persistent entity conditions using existing effect definitions and instances. | Hunger attaches to Alice and stains attach to her particular robes, without adding a parallel condition-instance model or changing reusable item definitions. | 2026-10-08 |
| Allow effects to contribute descriptive fragments as well as attribute modifiers. | Descriptions can reflect current world state across text and graphical interfaces; cleaning removes the underlying effect rather than editing descriptive strings. | 2026-10-08 |
| Classify effect definitions with tags and let actions query active attached effects. | Soap can match stain and washable properties without enumerating every stain definition; effectsOn returns detached snapshots and effectDefinition exposes classification. | 2026-10-08 |
| Support explicit effect removal in structured world changes. | Eating can remove hunger and cleaning can remove selected stain instances while preserving unrelated effects. | 2026-10-08 |
| Treat an effect without a lifetime as persistent until explicitly removed. | Stains remain through time advancement and unequipping; applicability predicates can still make other attached effects inactive. | 2026-10-08 |
| Supply random draws through an engine-owned context dependency. | Tests can force spill and no-spill outcomes; behaviors do not access ambient randomness. The prototype default engine source uses Math.random, and replay/state rollback of the random generator remains open. | 2026-10-08 |
| Stage supported action changes before committing world state. | Food consumption, hunger removal, and stain attachment succeed as a group; failures do not leave partial entity/effect changes. The staged executor currently supports consumption, attachment, and removal only. | 2026-10-08 |
| Resolve spill targets from currently worn body equipment. | The stain belongs to the worn garment instance; an unworn robe is not stained and item provenance can survive consumption of the stew. | 2026-10-08 |
| Provisional: stew has a 25% spill chance; a serving removes hunger; successful cleaning consumes one soap. | These are sample content and action semantics, not final rules for nutrition, portions, soap charges, or washing costs. Cleaning with no matching stains consumes nothing. | 2026-10-08 |
| Provisional: matching tags use all-of semantics and repeated description fragments are deduplicated. | Soap requires both stain and washable tags; repeated stains remain distinct effects while avoiding duplicate rendered text. Stain severity and accumulation policy remain open. | 2026-10-08 |
| Separate physical properties, compartment rules, ownership, and physical placement. | Owning an item does not mean carrying it; a worn scabbard may contain a sword without the sword being equipped. | 2026-10-08 |
| Give an entity one physical placement: carried, equipped, contained, or in the world. | A single relation avoids duplicate location truth. The existing equipment component is a compatibility projection; legacy owned fixtures default to carried placement. | 2026-10-08 |
| Represent containers with named compartments and referenced admission predicates. | Robes can expose independent left/right pockets, and each compartment can combine count, type, size, length, and burden rules. | 2026-10-08 |
| Use content-defined qualitative size and weight identifiers by default. | Most items do not need exact measurements; missing properties fail admission when the relevant rule needs them. | 2026-10-08 |
| Allow optional precise dimensions when a rule requires them. | A scabbard requires a known length strictly below one meter; exactly one meter or unknown length is rejected. Optional exact mass is modeled but not used by the current burden evaluator. | 2026-10-08 |
| Keep size capacity costs local to the compartment rule. | A pocket assigns extra-small a cost of 1 and small a cost of 2 against a budget of 2, without asserting a universal physical size ratio. | 2026-10-08 |
| Distinguish direct entity count, distinct definitions, and stack count; prototype uses direct entity count. | Ten separately represented coins count as ten even when they share a definition. Stacking and definition-count rules remain deferred. | 2026-10-08 |
| Include a nested container and all its contents in aggregate burden. | An anvil inside a pouch must not bypass the backpack capacity; size rules assess the outer item rather than adding its contents again. | 2026-10-08 |
| Reject self-containment and cycles, validate proposed contents, and commit moves atomically. | A failed move keeps source placement and equipment intact; nested weight additions revalidate enclosing container limits. | 2026-10-08 |
| Expose direct contents and recursively carried possessions separately from owned inventory. | Interfaces can show where items are while distinguishing a dropped but still owned item from a carried possession. | 2026-10-08 |
| Provisional: use configurable burden points, not physical mass, for weight classes. | Sample featherweight, bookweight, and anvilweight values are 1, 3, and 30; category boundaries, exact-mass conversion, and character carrying capacity remain open. | 2026-10-08 |
| Provisional: validate all compartments against staged moves and require ownership for item/container manipulation. | This small-world approach catches affected ancestor limits without a dependency index. Physical reach, permission sharing, locked containers, and descendant type policies remain open. | 2026-10-08 |
| Give armor separate reduceHit and reduceDamage attributes. | Shields may make attacks less likely to land while plate absorbs landed damage; the two defenses must not be conflated. | 2026-10-08 |
| Represent attacks as actions with explicit actor, weapon, and defender inputs. | Three participants cannot be expressed unambiguously by only sourceId and targetId; the shared context still supplies world access, time, and randomness. | 2026-10-08 |
| Store a weapon attack behavior reference, skill identifier, damage range, and damage type in its definition. | Ordinary sword mechanics are reusable content, while character skills, target dodge, equipped armor, and health remain entity state. | 2026-10-08 |
| Distinguish an attack miss from a rejected action and return a structured combat outcome. | A valid miss records hit chance and its random roll without causing damage; invalid equipment or dead participants reject the action. | 2026-10-08 |
| Use timed effects on weapon instances for enchantments and separate attack-specific contribution modules. | Flame can change description and target-dependent damage without overwriting base weapon damage or hard-coding enchantment identities into sword resolution. | 2026-10-08 |
| Use explicit applyDamage world changes and clamp resulting health at zero. | Damage is validated and staged before mutation; the prototype records slicing damage in the outcome and operation without allowing negative health. | 2026-10-08 |
| Provisional: hit chance is clamp(0.75 + 0.02 * (sword skill - dodge) - summed reduceHit, 0.05, 0.95). | reduceHit uses probability units (0.30 means thirty percentage points); sample coefficients and lower/upper bounds are balance placeholders. | 2026-10-08 |
| Provisional: roll inclusive integer weapon damage, multiply applicable bonuses, subtract summed flat reduceDamage, and clamp damage at zero. | Armor reduction remains meaningful against enhanced attacks. Equipped armor values add; misses draw no damage roll. Ordering and stacking are explicit prototype policies. | 2026-10-08 |
| Provisional: flame doubles slicing damage only against susceptible-to-fire targets for sixty seconds. | This implements the requested conditional multiplier without creating a separate fire-damage packet. Reapplication while active is rejected, and activation requires a learned Flame spell and an owned sword in hand. | 2026-10-08 |
| Defer full combat targeting, resource costs, and broader modifier gathering. | The prototype gathers attack contributions from the weapon only. Reach, turns, stamina/mana, critical hits, armor durability, typed damage packets, actor/environment modifiers, and progression balance remain open. | 2026-10-08 |
| Give sentient entities reusable versioned personality templates and independent instance state. | Flamebringer swords share starting voice, preferences, disposition, catchphrases, and behavior references, while each evolves independently. Personality providers are inherited from definitions. | 2026-10-08 |
| Represent affinity and resentment as separate per-subject relationship values. | A sword may like Alice while resenting inactivity; a new wielder gets a separate relationship rather than erasing history. | 2026-10-08 |
| Drive personality changes from committed world events with stable identities and historical facts. | Attack events capture target tags and outcomes at the time; rejected attacks emit none. Per-instance processed-event identities prevent duplicate relationship rewards. | 2026-10-08 |
| Use deterministic versioned behavior modules for relationship changes and simulation-time inactivity. | Read-only inputs produce updates independently of dialogue generation; evaluated-time checkpoints prevent repeated queries from applying the same inactivity penalty. | 2026-10-08 |
| Store selected memories and conversation records separately from the small personality state component. | Instances reference memories and retain continuing conversations without embedding entire transcripts in character or item components. Entity state and record snapshots support prototype restoration. | 2026-10-08 |
| Construct dialogue context from voice, disposition, listener relationship, preferences, relevant memories, recent messages, prior summary, and supplied observations. | A model receives meaningful bounded recent context without being handed the whole world. Observation selection is a caller perception contract; full visibility enforcement remains deferred. | 2026-10-08 |
| Use an adapter boundary for generated dialogue; text generation does not control gameplay state. | The prototype uses a deterministic stub. Replies cannot change health, affinity, or combat effects; proposed intentions or memory updates would require separate validation. | 2026-10-08 |
| Commit a conversation turn only after a valid reply and serialize responses per sword. | Adapter failures do not leave half a turn or mutate relationship state; concurrent replies are rejected by the prototype guard. | 2026-10-08 |
| Keep full transcripts and record summaries with their covered-message identity. | Longer conversations retain continuity while passing recent messages and older context separately. The prototype summary is an exact transcript excerpt; bounded semantic summarization is deferred. | 2026-10-08 |
| Provisional: icy attacks add 5 affinity, ease resentment by 2, and create a memory; each sixty idle simulation seconds adds 2 resentment. | Sample scores use a 0–100 range and any attack resets inactivity. Offline time does not advance automatically; real gameplay timing and persistence policy remain open. | 2026-10-08 |
| Provisional: speech opportunities rotate original catchphrases with a thirty-second cooldown. | The demo explicitly requests a blurt; direct dialogue also updates speech time. Autonomous scheduling, audience records for public speech, and personality-driven combat effects remain future work. | 2026-10-08 |
| Defer live LLM integration, durable event delivery, and advanced memory retrieval. | The prototype tests the intended context and state boundaries without choosing a provider, database, semantic summarizer, or production dispatcher. Event IDs are UUIDs; records remain in memory. | 2026-10-08 |
